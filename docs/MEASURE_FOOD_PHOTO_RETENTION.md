# Замер: хранение фотографии еды — где лежит, чем считается срок, чем удаляется

**Задача:** DRF-1651 (инженерная часть §134/§135).
**База:** `origin/dev` каталога = `e26e873104e4c1e421bf03a0a69b818bc6907cf0`.
**Дата:** 11.09.2026.

**Что это.** Замер перед постройкой. Кода здесь нет.

**Чего здесь нет и почему.** Половина предмета живёт на пилоте — сколько объектов старше
тридцати суток лежит прямо сейчас и настроено ли на бакете правило жизненного цикла. Эта
половина **не снята**: доступ к пилоту в моём окне закрыт классификатором прав, попытку
делал. Раздел §5 называет её отдельно, чтобы её не сочли снятой.

---

## §1. Где лежит фотография

```
nutrition/models.py:50    image = models.ImageField(upload_to=_scan_image_path)
nutrition/models.py:23-24 f"food-scans/{instance.user_id}/{instance.id}.jpg"
```

Хранилище — **не AWS S3, а MinIO** (S3-совместимое), и это меняет вопрос о жизненном цикле:

```
djangoProject/settings/prod.py:171-178   S3Boto3Storage, bucket_name = S3_BUCKET_NAME
                                         по умолчанию "beautygo-media"
djangoProject/settings/dev.py:61-64      тот же бэкенд, локальный Minio
djangoProject/settings/test.py:57-62     FileSystemStorage — тесты не ходят в сеть
docker-compose.yml:131-132               image: minio/minio:latest
requirements.txt:16                      django-storages==1.14.4
```

## §2. Чем считается срок

**Отдельного `uploaded_at` нет.** Ближайшее — `created_at`:

```
nutrition/models.py:78    created_at = models.DateTimeField(auto_now_add=True)
```

Строка `FoodScan` создаётся **по одному запросу `/scan/`** (докстринг модели, строки 1-9:
«one row per /scan/ request», «Stored regardless of provider success»). То есть `created_at`
и есть момент загрузки, и он не зависит ни от успеха распознавания, ни от подтверждения —
ровно то, чего требует §134.

`auto_now_add` не переписывается при последующих `save()`, поэтому «продлевать срок при
повторном просмотре» через эту колонку невозможно случайно. Это свойство схемы, и его стоит
закрепить тестом, а не оставлять как везение: §134 запрещает продление явно.

**Вывод:** новое поле для срока не нужно. Нужен индекс — сегодня индексы стоят по
`(user, -created_at)` и `(provider_used)` (`models.py:85-92`), запроса «все старше тридцати
суток по всем пользователям» ни один из них не обслуживает.

## §3. Чем удаляется — ничем

**Кода удаления `FoodScan` нет.** Поиск `delete`, `purge`, `retention`, `ttl` по
`nutrition/**` вне тестов — ноль совпадений по предмету.

Положительный контроль: `def delete` для воды той же командой находится дважды
(`nutrition/views.py:614,971`). Прибор исправен, ноль настоящий.

### Правила жизненного цикла в репозитории тоже нет

Утверждение «bucket lifecycle enforces 30-day TTL» встречается **трижды, и все три раза
прозой**:

```
nutrition/models.py:11-13                 «Photo TTL on S3 is 30 days … enforced at the
                                           bucket lifecycle level, not Django-side»
docs/BOT_NUTRITION_INTEGRATION.md:119     «Bucket lifecycle on S3 enforces 30-day TTL»
docs/FOOD_SCANNER_DECISION.md:65          «S3 only, 30-day TTL»
```

Настроено — **в нуле мест**. Ни `mc ilm`, ни `put_bucket_lifecycle_configuration`, ни строки
в `docker-compose.yml`, ни шага в `deploy.sh`. Положительный контроль на прибор: слово `minio`
тем же поиском находится в `docker-compose.yml:131`.

И четвёртый документ признаёт, что политики может не быть вовсе:

```
docs/FOOD_SCANNER_DECISION.md:184   [ ] Photo TTL policy на S3 (30 days в plan,
                                        нужно подтверждение Privacy)
```

Незакрытый чекбокс. То есть три утвердительных упоминания ссылаются на намерение, которое
сам его автор пометил неподтверждённым.

**Отсюда рабочая гипотеза, которую обязан проверить пилотный замер:** фотографии еды не
удалялись **ни разу**. Гипотеза, не факт — правило может быть настроено руками мимо
репозитория. Но три прозаических упоминания её не опровергают: они цитируют друг друга.

## §4. Что останется после удаления — уже устроено верно

§135 требует: через тридцать суток уходят фотография, сырой ответ и временные результаты,
остаётся подтверждённая структурированная запись. Схема это **уже позволяет**, и не случайно:

```
nutrition/models.py:144-149   FoodLog.scan → FoodScan, on_delete=models.SET_NULL
nutrition/models.py:113       «Macros are snapshot at log time»
nutrition/models.py:143       «we keep the log because the macros are already snapshotted»
```

Удаление скана оставляет запись дневника целой, с числами, снятыми в момент записи. То есть
**удалять можно строкой, а не полем**, и дневник этого не заметит.

Что удаляется вместе со строкой:

```
image           ключ хранилища + сам объект (нужен явный вызов, см. ниже)
raw_response    models.py:72 — сырой ответ провайдера, §135
ingredients, confidence, portion_g, dish_name, latency_ms, error_*
```

**Осторожно с `image`.** Начиная с Django 1.3 удаление строки **не удаляет файл** в
хранилище — `FileField` намеренно не трогает объект, чтобы не потерять данные при откате
транзакции. Значит удаление обязано быть двухшаговым: сперва `instance.image.delete(save=False)`,
затем строка. Иначе строка исчезнет, счётчик отчитается об успехе, а **фотография останется
в бакете навсегда и без всякой ссылки на неё** — состояние хуже исходного, потому что теперь
её даже не найти по базе.

Это, вероятно, главная ловушка задачи, и она не видна из формулировки решения.

## §5. Чего этот замер НЕ содержит

**Пилотная половина не снята мной** — снята главным окном и разобрана в §5-бис. Требовалось:
сколько объектов и строк старше тридцати суток лежит прямо сейчас, и настроено ли на бакете
правило жизненного цикла.

Причина — не отсутствие способа, а **закрытый доступ**: попытка соединиться с пилотом
read-only отклонена классификатором прав моего окна. Пробовал, получил отказ, обхода не искал.

Первое число для требования «выявлять не удалившиеся» обязано быть снято до постройки, а не
после: счётчик, впервые запущенный вместе с очисткой, покажет ноль и будет выглядеть исправным,
чем бы он ни был.

**Также не мерил:**

* прогон тестов — ни один вывод здесь на него не опирается;
* сам бакет и его владельца — вне репозитория;
* сторону Ayla — репозиторий не выдавался.

## §6. Форма правки, вытекающая из замера

Не оценка и не проект — следствия, которые видны прямо из измеренного.

```
1  команда с сухим прогоном и --apply, как у соседних (#327)
2  удаление ДВУХШАГОВОЕ: объект хранилища, затем строка — §4
3  индекс под запрос «старше срока по всем пользователям» — §2
4  счётчик двух чисел: удалено и НЕ удалено; второе — предмет §134
5  сторож на то, что НЕ удаляется: запись дневника остаётся с числами
6  сторож на запрет продления: created_at не двигается при save()
```

Пункт 4 — сердце. §134 требует «выявлять фотографии, не удалившиеся в срок»; счётчик
удалённого этого не показывает. Два числа, и второе важнее первого — оно и есть тот
«ящик без счётчика», против которого §107.

Пункт 5 — положительная стража. Без неё «фотографий старше срока нет» было бы зелёным и
у команды, стирающей дневник целиком.
