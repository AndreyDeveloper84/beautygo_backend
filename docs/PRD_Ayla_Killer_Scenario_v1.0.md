## 0. Назначение этого документа

Этот PRD **не дублирует и не заменяет** базовый PRD Ayla v3.0. Он операционализирует **один конкретный сценарий** — killer scenario из Vision и Appendix B базового PRD — и превращает его из нарратива в измеримую, поставляемую инициативу.

**Зачем отдельный документ:**
В базовом PRD killer scenario существует только как иллюстрация. Phase 1 (Food Scanner) и Phase 2 (AI-аватар) запланированы как отдельные фичи. Но **ценность killer scenario возникает только в их связке через память** — а связка нигде не описана как фича. Если мы построим Phase 1 и Phase 2 параллельно без явной интеграции, мы получим два изолированных продукта и ноль killer moments.

Этот PRD фиксирует killer scenario как **приёмочный критерий MVP**: если пользователь не проходит этот сценарий — мы не достигли PMF, даже если все фичи технически работают.

## 1. Problem Statement

### 1.1. Какую проблему решаем

**Базовая проблема (из Vision):** Self-care требует слишком много когнитивных усилий — слишком много решений, инструментов, ручной координации. Пользователь откладывает, забывает, теряет контекст.

**Проблема внутри Ayla MVP, которую решает именно killer scenario:**
В Ayla MVP есть три сильные, но **разрозненные** фичи: Food Scanner (Phase 1), AI-аватар (Phase 2) и AI-запись к мастеру (Phase 0). Каждая по отдельности — это очередное приложение в категории. Без явной связки через память Ayla = MyFitnessPal + FaceApp + Yclients-конкурент в одном бандле. **Это не killer product.**

Killer scenario — это единственный сценарий, в котором становится видно, **зачем эти три фичи в одном продукте**. Без него вся продуктовая ставка на «AI, который помнит» — слова без доказательства.

### 1.2. Что происходит без этого PRD

| Без killer scenario как явной фичи | С killer scenario как явной фичей |
|---|---|
| Food Scanner = ещё один трекер питания | Каждое сканирование строит модель пользователя |
| AI-аватар = разовое развлечение | Прогресс привязан к питанию и услугам — есть причинно-следственная связь |
| Запись к мастеру = ещё одна форма | Ayla сама предлагает услугу под текущее состояние пользователя |
| Память = техническая фича в бэклоге | Память = моат, видимый пользователю каждый день |
| 3 разрозненные метрики retention | Один интегральный metric: % пользователей, прошедших killer flow |

### 1.3. Доказательства проблемы

- **Из Vision:** «Никто на рынке СНГ не строит персонального AI-компаньона с памятью, ориентированного на клиента»
- **Из CLAUDE.md проекта:** 47% клиентов откладывают запись из-за паралича выбора
- **Косвенно:** ни одна из конкурирующих фич (MyFitnessPal, FaceApp, Yclients) не имеет cross-domain связки — все они монопродуктовые
- **Что нужно для финальной валидации (закрыть до Sprint 1):** 5+ глубинных интервью с целевой персоной, в которых явно обсуждается реакция на полный killer flow (мокап + сценарий)

## 2. The Killer Scenario — операционализация

### 2.1. Нарратив (из Vision)

> Утром пользователь фотографирует завтрак. Ayla анализирует питание и замечает дефицит витамина D. Рекомендует массаж с аргановым маслом — мастер Анна рядом, свободна завтра вечером. Пользователь записывается в два нажатия. Вечером обновляет AI-аватар. Ayla показывает: за месяц кожа стала ровнее — вот прогресс. Пользователь делится в Telegram.

### 2.2. Декомпозиция на шаги (operational view)

| # | Шаг | Что делает пользователь | Что делает Ayla | Какая capability нужна | Из какой Phase |
|---|---|---|---|---|---|
| **S1** | Утренний snap | Фотографирует завтрак | Распознаёт еду + макро- и микронутриенты | Food Scanner | Phase 1 |
| **S2** | Анализ контекста | Ничего | Сравнивает с историей за 7+ дней, находит паттерн дефицита | **Memory + Insight Engine** | НОВОЕ |
| **S3** | Cross-domain переход | Видит инсайт «у тебя дефицит витамина D 5 дней подряд» | Связывает биологический сигнал с beauty-услугой | **Cross-domain rules engine** | НОВОЕ |
| **S4** | Персональная рекомендация | Видит карточку «Массаж с аргановым маслом у Анны, завтра 19:00» | Подбирает мастера: знает, что Анна — любимый, рядом, свободна | **Memory + Booking Engine** | Phase 0 + Memory |
| **S5** | Запись в 2 тапа | Тап «забронировать» → тап «подтвердить» | Создаёт appointment, оплачивает | Booking + YooKassa | Phase 0 |
| **S6** | Вечерний snap аватара | Делает selfie / обновляет AI-аватар | Сравнивает с baseline, считает дельту | AI-аватар | Phase 2 |
| **S7** | Прогресс-вью | Видит «за месяц кожа ровнее на N%» | Связывает прогресс с историей питания + услуг | **Memory + Avatar timeline** | Phase 2 + Memory |
| **S8** | Шеринг | Тап «поделиться» → Telegram | Генерирует красивую карточку прогресса | **Shareable artifact** | Phase 2 |

**Критическое наблюдение:** Шаги S2, S3, S7 — это **не Phase 1, не Phase 2, а Phase 1.5** — слой памяти и cross-domain логики, который **сейчас никем не запланирован**. Без этого слоя killer scenario технически невозможен, даже если все остальные фичи готовы.

### 2.3. Минимально достаточная версия (MVP-of-MVP)

Полный сценарий S1→S8 — это финальное состояние. Для первой валидации можно поставить более скромную версию:

**v0.1 — Half Killer Scenario (только утренняя половина)**
S1 → S2 → S3 → S4 → S5. Без аватара и шеринга. Доказывает: cross-domain insight + персональная рекомендация работает и приводит к записи.

**v0.2 — Full Killer Scenario**
+ S6, S7, S8. Доказывает: ежедневная привычка и виральность.

Рекомендую **поставить v0.1 первым** — это самый быстрый способ проверить, работает ли центральная гипотеза, не дожидаясь готовности AI-аватара (Phase 2).

## 3. Goals & Success Metrics

### 3.1. Goals

1. **Доказать, что Ayla = больше, чем сумма фич.** Метрика: % активных пользователей, у которых хотя бы одна запись была инициирована рекомендацией от Food Scanner (а не вручную через поиск)
2. **Сократить time-to-magic.** Метрика: медианное время от первого открытия приложения до первого killer moment (S1-S5 завершён)
3. **Доказать, что память создаёт ценность.** Метрика: разница в качестве рекомендаций между cohort 7-day и cohort 30-day (CTR на рекомендацию, конверсия в запись)
4. **Создать виральный артефакт.** Метрика: % пользователей, которые шерят прогресс хотя бы один раз в первые 30 дней

### 3.2. Success Metrics — конкретные таргеты

> Эти метрики **дополняют**, а не заменяют метрики базового PRD v3.0.

| Метрика | Baseline | Target (60 дней после запуска v0.1) | Target (90 дней после v0.2) | Источник |
|---|---|---|---|---|
| **% активных пользователей с ≥1 killer moment / неделю** | 0% | ≥ 25% | ≥ 40% | Funnel analytics |
| **Time-to-first-killer-moment (медиана, новые юзеры)** | n/a | ≤ 5 дней | ≤ 3 дня | Cohort analysis |
| **CTR на cross-domain insight карточку** | n/a | ≥ 18% | ≥ 25% | Event tracking |
| **Конверсия insight → запись** | n/a | ≥ 8% | ≥ 12% | Funnel |
| **% записей, инициированных Ayla (а не ручным поиском)** | 0% | ≥ 20% | ≥ 35% | Booking source attribution |
| **Memory enrichment rate** (новых фактов о пользователе/неделю) | 0 | ≥ 5 | ≥ 12 | Memory store telemetry |
| **Шеринг прогресса (% юзеров за 30 дней)** | 0% | n/a (v0.1 без аватара) | ≥ 20% | Share intent events |
| **Качество памяти** (manual review корректности фактов) | n/a | ≥ 85% | ≥ 92% | QA-выборка по 100 юзерам |

**Главная метрика (North Star для этого PRD):** % активных пользователей с ≥1 killer moment в неделю. Если она ниже 15% к 60-му дню — killer scenario не работает, нужна стратегическая переоценка, а не точечные правки.

## 4. Non-Goals

Что **сознательно вне скопа** этого PRD:

1. **Не строим general-purpose memory.** Память хранит только то, что нужно для killer scenario: пищевые паттерны, любимые мастера, baseline внешности, история услуг. Не разговорная история. Не эмоции. Не цели «похудеть к лету».
2. **Не делаем медицинские диагнозы.** «Дефицит витамина D» — это **сигнал-нотификация**, а не медицинский вывод. Юридически это insight о питании, не о здоровье. Формулировки проверяются Legal до запуска.
3. **Не строим Insight Engine как ML-модель.** В v0.1 — rules-based с человекочитаемыми правилами, которые редактируются продактом. ML — после 1000+ killer moments в логах.
4. **Не интегрируемся с wearables и health-данными в этом PRD.** Apple Health, Google Fit, anyaздана — отдельная инициатива.
5. **Не делаем proactive push «Ayla заметила дефицит».** В v0.1 инсайт показывается **только при открытии приложения** после сканирования. Проактивные пуши — после валидации, что не раздражают (отдельный safety-протокол).
6. **Не покрываем шаги S6-S8** в v0.1. Они входят в v0.2.
7. **Не строим казахскую локализацию.** Killer scenario сначала валидируется в Пензе на русском.

## 5. Target Persona — для этого сценария

Базовый PRD описывает Segment A широко (женщины 22–40, городские, бьюти-юзеры). Для killer scenario нужна **более узкая первичная персона**, иначе сценарий размажется.

**Primary persona — «Алина, 28»**
- Город: Пенза
- Профессия: маркетолог в IT-компании
- Регулярно пользуется бьюти-услугами (1–2 услуги в неделю)
- Уже пробовала MyFitnessPal — забросила через 2 недели (надоело логировать)
- Подписана на 3+ wellness-блогеров в Telegram
- Использует Instagram/VK для поиска мастеров — её бесит хаос и переписки
- Готова попробовать AI, но скептична: «GPT-боты — это игрушка»

**Что Алина должна почувствовать после killer moment:**
> «Подожди. Оно что, реально связало мой завтрак с записью к Анне? И знает, что Анна — мой любимый мастер? Это не приложение, это какая-то магия. Надо подруге показать.»

Если это чувство **не возникает** в первые 7 дней — killer scenario провален, даже если все метрики формально на таргете.

### 6.2. Memory Model (минимально достаточная для killer scenario)

> **Это самая важная часть PRD.** Без явного контракта памяти killer scenario не существует.

В v0.1 память — **structured, не embeddings**. Embeddings/RAG — после валидации.

**Memory entities (v0.1 schema):**

```python
# Pseudocode — финальная схема в Sprint 0

class UserMemory:
    user_id: UUID

    # 1. Nutrition patterns (rolling 30 days)
    nutrition_summary: {
        avg_calories_per_day: float
        macro_balance: {protein, fat, carbs}
        micronutrient_flags: [
            {nutrient: "vitamin_d", status: "deficit", confidence: 0.82, since: date}
        ]
        last_7_meals: [MealRef]
    }

    # 2. Beauty preferences
    beauty_profile: {
        favorite_specialists: [SpecialistRef]  # weighted by recency + repeat bookings
        favorite_services: [ServiceCategoryRef]
        avg_service_price: int
        preferred_time_slots: [TimeWindow]
        preferred_district: str
    }

    # 3. Avatar baseline (для v0.2)
    avatar_baseline: {
        first_avatar_date: date
        skin_tone: str
        skin_evenness_score: float  # 0..1
        history: [AvatarSnapshot]
    }

    # 4. Interaction memory
    interaction: {
        last_active: datetime
        total_killer_moments: int
        rejected_recommendations: [RecRef]  # to NOT repeat
    }
```

**Принципы памяти:**
- **Explicit, not implicit.** Каждый факт имеет источник: «дефицит витамина D» — потому что 5 дней подряд в логах < 30% от RDA. Пользователь может тапнуть и увидеть «откуда Ayla это знает».
- **User-editable.** Любой факт можно удалить или поправить. UI — экран «Что Ayla обо мне знает».
- **Graceful degradation.** Если памяти ещё нет (новый юзер) — рекомендации работают, но без персонализации. Killer scenario недостижим до накопления N=5 сканирований и ≥1 завершённой записи.
- **152-ФЗ compliant.** Все данные на серверах в РФ. Кнопка «Удалить всё» удаляет в течение 24 часов. См. T1 Risk Register.

### 6.3. Insight Engine (rules-based v0.1)

В v0.1 — **жёсткий список правил**, написанный продактом + nutritionist-консультантом, ревью Legal. Без LLM-генерации правил.

**Пример правила (формат):**
```yaml
rule_id: vitamin_d_deficit_to_argan_massage
trigger:
  type: nutrition_pattern
  condition: vitamin_d_intake_pct_rda < 30
  window_days: 5
  min_data_points: 3
insight_text: "За последние {N} дней витамин D ниже нормы — это часто отражается на коже"
recommendation:
  type: beauty_service
  service_category: massage
  service_modifier: argan_oil
  rationale_text: "Массаж с аргановым маслом помогает коже получить больше витамина E и F"
disclaimer: "Это не медицинская рекомендация. При стабильном дефиците обратитесь к врачу."
priority: medium
cooldown_days: 7  # don't repeat same insight more than once a week
legal_reviewed: true
legal_review_date: TBD
```

**Целевое количество правил для v0.1 launch:** 8–12 (покрывают самые частые паттерны: дефицит витаминов D/B12/Fe, переизбыток сахара, обезвоживание, недостаток омега-3 и т.д.)

### 6.4. Recommendation Composer

Алгоритм (v0.1):
1. Получить активные insights из Insight Engine для текущего пользователя
2. Для каждого insight выбрать candidate-услугу из правил
3. Найти доступных мастеров для услуги: фильтр по `beauty_profile.preferred_district`, `preferred_time_slots`
4. Boost мастеров из `favorite_specialists` (×1.5 в score)
5. Проверить реальную доступность через Booking Engine (Phase 0)
6. Вернуть top-1 рекомендацию (не список! Killer scenario про «решение, не выбор»)
7. Логировать всё в `recommendation_events` для funnel analytics

## 11. Recommendation

**Решение:** Запустить как отдельную инициативу-«линзу» поверх Phase 1 + Phase 2 базового PRD.

**Обоснование:**
1. Killer scenario — **единственный** доказательный сценарий для центральной гипотезы продукта («Ayla помнит и связывает»). Без него PMF недостижим, даже если все остальные метрики на таргете
2. Связка между Phase 1 и Phase 2 нигде не описана как фича — без этого PRD она не появится
3. Memory как явная фича сейчас отсутствует в roadmap — это критический пробел
4. v0.1 (Half Killer) можно поставить **до готовности Phase 2**, что ускоряет валидацию центральной гипотезы

**Что меняется в базовом PRD v3.0 при принятии этого PRD:**
1. Phase 1 (Food Scanner) расширяется: добавляется Memory Store и Insight Engine
2. Phase 2 (AI-аватар) расширяется: добавляется timeline и интеграция с Memory
3. Появляется новая Phase 1.5 — «Killer Scenario v0.1»
4. Метрики секции 3.2 этого PRD добавляются в Success Metrics базового PRD
5. Risk Register пополняется K-R1…K-R6

**Следующий шаг при approve:**
- Андрей утверждает PRD → планируется Sprint 0 (неделя архитектуры памяти + Legal kickoff) → к концу Sprint 0 закрываются Open Questions 1, 2, 5, 6 → дальше Sprint 1 v0.1 Alpha
