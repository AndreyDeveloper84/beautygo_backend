# Payments capture strategy (pilot): немедленный capture, параметризуемая задержка

> **Status:** Accepted — 2026-07-18 (решение владельца, сессия оркестрации).
> Связано: Decision Log D9 (`docs/PROJECT_INDEX.md` §5.4), аудит payments от 2026-07-18, бриф W1 (`docs/PILOT_STREAMS_2026-08-15.md`), ADR-0009.

## Терминология

Речь о **capture** — подтверждении/списании двухстадийного платежа YooKassa
(`capture=false` при создании → `waiting_for_capture` → отдельный запрос
capture). Не путать с «капчей». Отменить можно только платёж в
`waiting_for_capture`; после перехода в `succeeded` — только возврат (refund).

## Context

- Аудит 2026-07-18: `capture_payment` (`payments/services.py:140`) не
  вызывается нигде в продовом коде — холды сгорают или подтверждаются вручную
  в ЛК ЮKassa. Денежный контур незамкнут.
- Модель пилота (D1/D6/D8): клиент может платить онлайн (опционально), split
  per-master, 90₽ платформе при capture.
- Отложенный capture (T+24) даёт антифрод-окно и мгновенную отмену холда
  вместо refund, но сдвигает выплату всем мастерам на сутки.

## Decision

**В пилоте применяется немедленный capture после подтверждения факта оказания
услуги: `CAPTURE_DELAY_HOURS=0`.**

При этом механизм capture реализуется как **параметризуемая отложенная задача**
и изначально поддерживает значение больше нуля. Переход на 24 часа — сменой
конфигурации, без переделки платёжного контура.

```yaml
payments:
  two_stage: true
  capture_delay_hours: 0
  capture_safety_buffer_minutes: 60
  capture_trigger: service_completed
  reconciliation_enabled: true
  overdue_capture_alert_enabled: true
```

## Почему

- мастера быстрее получают деньги (supply пилота ограничен, первый опыт
  критичен);
- ручной Concierge-контроль первых 100–500 пользователей снижает ценность
  окна разбирательства;
- ожидаемое число споров невелико;
- не усложняем клиентский UX вторым банковским событием через сутки
  (риск «двойного списания» в восприятии);
- переход на 24 часа не требует переделки.

## Когда переключаем на 24 часа

Не «при открытии второго города» автоматически, а по измеримым триггерам —
хотя бы одному из:

- растёт число жалоб после визита;
- возвраты и chargeback становятся заметной стоимостью;
- Concierge Mode больше не обеспечивает ручной контроль;
- появляется SLA поддержки, позволяющий разобрать спор внутри окна;
- продуктовая команда подтверждает, что задержка выплаты не ухудшит
  supply retention.

## Обязательные технические условия

### 1. Планировать capture относительно `expires_at`

Фактический срок capture зависит от способа оплаты и передаётся ЮKassa в
`expires_at` — по документации от двух часов до семи дней. Нельзя
ориентироваться на условные «7 дней». Если срок истечёт, платёж отменится с
причиной `expired_on_capture`, деньги разморозятся.

```python
safe_capture_deadline = expires_at - CAPTURE_SAFETY_BUFFER  # 60 минут
capture_at = min(
    completed_at + timedelta(hours=CAPTURE_DELAY_HOURS),
    safe_capture_deadline,
)
```

Иначе для способа оплаты с коротким холдом конфигурация на 24 часа приведёт
к автоматической отмене платежа.

### 2. Capture должен быть идемпотентным и восстанавливаемым

Celery Beat — не единственный механизм. Обязательны:

- уникальный idempotency key на capture;
- блокировка повторной обработки;
- повторные попытки с backoff;
- периодический reconciliation job;
- алерт по платежам, приближающимся к `expires_at`;
- алерт по визитам `completed`, у которых платёж остался
  `waiting_for_capture`;
- обработка webhook от ЮKassa;
- ручная management-команда повторного запуска capture.

## UX-статусы (не показывать `waiting_for_capture` пользователям)

**Клиент:**

| Внутренний статус | Что видит клиент |
|---|---|
| `PAYMENT_AUTHORIZED` | Деньги зарезервированы |
| `PAYMENT_CAPTURE_SCHEDULED` | Оплата будет подтверждена после визита |
| `PAYMENT_CAPTURED` | Оплата завершена |
| `PAYMENT_RELEASED` | Резерв отменён, деньги разблокированы |

**Мастер:** Ожидает завершения визита → Готово к списанию → Оплата
подтверждена → К выплате → Выплачено.

## Продуктовая оговорка (копирайтинг)

При `CAPTURE_DELAY_HOURS=0` окно спора после факта оказания услуги
практически исчезает. Клиенту **нельзя** обещать «у вас будет 24 часа на
жалобу до списания».

Корректная формулировка для пилота:

> «Сумма резервируется при записи и списывается после подтверждения оказания
> услуги. Если возникла проблема, обратитесь в поддержку».
