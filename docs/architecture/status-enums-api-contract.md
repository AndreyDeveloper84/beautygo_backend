# Status enums — API contract (Phase 5, P1-2)

> **Phase 5 OpenAPI follow-up.** Documents the three `status` enums that
> share the schema namespace, their canonical OpenAPI component names
> (pinned by PR #186), allowed values, lifecycle transitions, and the
> internal→spec mappings. No code change — this is the contract-of-record
> for mobile/bot codegen consumers.
>
> **Source of truth:** the code. This doc is regenerated by hand when an
> enum changes; the `spectacular` schema is regenerated by `make` on
> demand. If they disagree, the code wins — open a drift ticket.
>
> **Audited:** 2026-06-03 (Alpha). Companion to PR #186 (drf-spectacular
> warnings → 0).

## Why this doc exists

The schema has **three distinct `status` fields** on three unrelated
models. drf-spectacular derives a component-schema name from each enum;
left alone it collides them into auto-suffixed names (`Status56bEnum`,
`Status…Enum`) that are unstable across schema regenerations — every
field reshuffle renames the generated type, breaking mobile/bot codegen.

PR #186 pinned the names via `SPECTACULAR_SETTINGS['ENUM_NAME_OVERRIDES']`
in `djangoProject/settings/base.py`:

| OpenAPI component | Backing Choices class |
|---|---|
| `AppointmentStatusEnum` | `appointments.models.Appointment.Status` |
| `PaymentStatusEnum` | `payments.models.Payment.Status` |
| `SpecialistProfileStatusEnum` | `users.models.SpecialistProfile.ProfileStatus` |

This doc is the human-readable contract those pinned names point at.

## 1. AppointmentStatusEnum

`appointments.models.Appointment.Status` (`models.TextChoices`).

| Value | Label (ru) | Holds slot? | Terminal? |
|---|---|---|---|
| `pending` | Ожидает подтверждения | ✅ | — |
| `awaiting_payment` | Ожидает оплаты | ✅ | — |
| `confirmed` | Подтверждена | ✅ | — |
| `in_progress` | В процессе | — | — |
| `completed` | Завершена | — | ✅ |
| `cancelled` | Отменена | — | ✅ |
| `no_show` | Клиент не пришёл | — | ✅ |

**Slot-holding** (`ACTIVE_BOOKING_STATUSES`, block future bookings):
`pending`, `awaiting_payment`, `confirmed`.

**Terminal** (`TERMINAL_STATUSES`, no further transitions):
`completed`, `cancelled`, `no_show`.

### Lifecycle (enforced by `BookingStateMachine`)

```
pending ─────────► awaiting_payment ─────► confirmed ─────► completed
   │                     │                    │
   └──► cancelled        └──► cancelled        ├──► cancelled
                                               └──► no_show
```

Transition table — single source of truth is
`appointments/domain/value_objects.py::_BOOKING_TRANSITIONS`:

| From | Allowed targets |
|---|---|
| `pending` | `awaiting_payment`, `cancelled` |
| `awaiting_payment` | `confirmed`, `cancelled` |
| `confirmed` | `completed`, `cancelled`, `no_show` |
| `completed` / `cancelled` / `no_show` | — (terminal) |

### ⚠️ Contract nuance: `in_progress` is model-only

`in_progress` exists on the **model** enum (`Appointment.Status`) but
is **NOT** part of the domain `BookingStatus` enum or
`_BOOKING_TRANSITIONS`. The `BookingStateMachine` neither produces nor
accepts it. It is a presentational/manual status with no enforced
transition path. Consumers must treat `in_progress`:

- as a **valid response value** (it can appear on a serialized
  appointment), but
- **not** as a state reachable via the documented transition table.

If a future ticket folds `in_progress` into the state machine, update
both `_BOOKING_TRANSITIONS` and this section together.

## 2. PaymentStatusEnum

`payments.models.Payment.Status` (`models.TextChoices`). The **internal**
status set is wider than the **API spec** status set; the serializer
maps internal→spec on the way out.

### Internal values

| Internal value | Label (ru) |
|---|---|
| `pending` | Ожидает |
| `authorized` | Авторизован |
| `paid` | Оплачен |
| `failed` | Ошибка |
| `refunded` | Возвращён |
| `partially_refunded` | Частичный возврат |

### Internal → API spec mapping

Spec PaymentStatus is the closed set `pending | succeeded | failed |
refunded`. Mapping is `payments/serializers.py::_STATUS_TO_SPEC`:

| Internal | API response |
|---|---|
| `pending` | `pending` |
| `authorized` | `pending` _(hold in progress → still pending)_ |
| `paid` | `succeeded` |
| `failed` | `failed` |
| `refunded` | `refunded` |
| `partially_refunded` | `refunded` |

**Note for codegen consumers:** the `PaymentStatusEnum` component in the
generated OpenAPI reflects the **internal** Choices values (that's what
the model field declares). The serialized `status` field on a payment
**response** carries the **spec** value (`succeeded`, never `paid`).
This is an intentional asymmetry — the model is the storage contract,
the response is the API contract. Bind response parsers to the spec set,
not the component enum.

## 3. SpecialistProfileStatusEnum

`users.models.SpecialistProfile.ProfileStatus` (`models.TextChoices`).
Third `status` field in the schema — the override exists specifically
because without it drf-spectacular falls back to `Status56bEnum`.

| Value | Label (ru) | Meaning |
|---|---|---|
| `draft` | Черновик | Profile created, not submitted for verification |
| `pending` | На верификации | Submitted, awaiting moderator review |
| `active` | Активен | Verified — visible in the public catalogue |

No formal state machine class; the progression is linear
(`draft → pending → active`) and enforced at the view/service layer, not
by a dedicated transition table. This doc does not pin transition rules
for it — only the value set and meanings.

> ⚠️ Naming collision with `AppointmentStatusEnum`: both have a
> `pending` value with different semantics (appointment awaiting
> confirmation vs profile awaiting verification). They are **different
> enums** — never compare across them. The pinned component names exist
> precisely to keep them as separate types in generated clients.

## Change protocol

When you add/remove/rename a value on any of the three enums:

1. Update the model `Choices` class (source of truth).
2. Update the matching table in this doc.
3. If it's an Appointment status, update `_BOOKING_TRANSITIONS` and the
   lifecycle diagram in §1 in the **same** PR.
4. If it's a Payment status, update `_STATUS_TO_SPEC` (every internal
   value MUST map to a spec value) in the **same** PR.
5. Regenerate the schema and confirm zero new enum warnings.

Refs: PR #186 (drf-spectacular warnings → 0), `ENUM_NAME_OVERRIDES` in
`djangoProject/settings/base.py`, codex api-spec-contract-drift audit,
Phase 5 (parallelisable filler).
